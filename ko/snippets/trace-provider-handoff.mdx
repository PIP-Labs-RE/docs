# Trace Provider 데이터 감사 — 통합 및 API 레퍼런스

Trace 데이터 감사 API의 단일 정보 출처(single source of truth): provider 온보딩, 인증, Trace Schema, 쓰기 및 읽기 엔드포인트, 검색, 통계, scoped 그룹, 제한, 그리고 검증에 관한 문서입니다.

<Note>
이 API와 Trace Schema는 provider에 구애받지 않습니다(provider-agnostic) — 모든 provider는 동일한 엔드포인트, 헤더, 스키마를 통해 통합됩니다. 예제에서는 실제 운영 중인 provider인 **Kled**를 사용합니다. Kled가 등장하는 모든 곳을 본인 provider의 식별 정보로 대체하시면 됩니다.
</Note>

## 환경(Environments)

| 환경 | Base URL | 인증 |
| --- | --- | --- |
| **Staging** | `https://staging-api.storyprotocol.net` | 쓰기는 스테이징 API 키로 게이팅됩니다. 읽기는 공개입니다. |
| **Production** | `https://api.dataapis.io` | 쓰기는 프로덕션 API 키로 게이팅됩니다. 읽기는 공개입니다. |

Staging은 새로운 provider 통합을 온보딩하고 테스트하는 환경입니다. Production은 배포되어 있지만 아직 provider 데이터가 없을 수 있습니다 — 프로덕션 트래픽을 보내기 전에 DATA Foundation 팀에 확인하십시오.

## 접근 권한 얻기

<Info>
쓰기 접근은 게이팅되어 있습니다. 통합 전에 DATA Foundation 팀에 연락해 온보딩을 받으십시오. 저희가 provider 식별 정보를 화이트리스트에 등록하고, 스테이징 및 프로덕션 API 키를 발급하며, 쓰기 요청에 사용해야 하는 `X-Provider` 값을 할당합니다. 이 과정이 완료되기 전까지는 쓰기 요청이 거부됩니다. 읽기, 검색, scoped 그룹 엔드포인트는 공개된 감사 뷰이므로 키가 필요하지 않습니다.
</Info>

## 인증 및 provider 범위

모든 쓰기 요청에는 다음 헤더가 포함되어야 합니다:

```text
X-API-Key: <provider API key for the target environment>
X-Provider: kled
X-Batch-Id: <stable batch id>
```

- API 키는 본인 provider에 속해야 하고 `X-Provider`와 일치해야 합니다. 대상 환경에 해당하는 키를 사용하십시오.
- 백로그(backlog) 적재의 경우 `X-Ingestion-Source: backlog`를 추가하십시오. 라이브 적재의 경우 헤더를 생략하십시오 — 명시적인 `live` 값은 허용되지 않습니다.
- 읽기 API는 전역 `data_id`로 키가 지정됩니다. `provider`는 필드로 반환되며 선택적 필터로도 사용됩니다.

<Warning>
읽기, 검색, scoped 그룹 엔드포인트는 **공개 감사 뷰**입니다. 엔터프라이즈 전용이거나 민감한 필드를 공개 Trace 페이로드에 넣지 마십시오. provider 전용 또는 파트너 전용 읽기 계층이 필요해질 경우, 이는 별도의 API/제품 결정 사항입니다.
</Warning>

## 적재(Ingestion) 흐름

<Steps>
  <Step title="배치 전송">
    provider 클라이언트가 webhook 배치 엔드포인트로 POST 요청을 보냅니다.
  </Step>
  <Step title="비동기 처리">
    수락된 항목은 큐에 적재되어 DATA Foundation에서 비동기적으로 처리됩니다.
  </Step>
  <Step title="다시 읽기">
    레코드는 읽기 및 검색 엔드포인트를 통해 조회할 수 있게 됩니다.
  </Step>
</Steps>

`records:batch` 응답에는 항상 항목별 상태가 포함됩니다:

- `202 Accepted` — 최소 하나의 항목이 비동기 처리를 위해 수락되었고 충돌한 항목이 없습니다.
- `200 OK` — 모든 항목이 중복이어서 새로운 비동기 작업이 큐에 등록되지 않았습니다.
- `409 Conflict` — 최소 하나의 항목에서 충돌이 발생했습니다. 같은 응답에 포함된 `accepted` 항목은 정상적으로 큐에 등록됩니다.

각 항목의 상태를 확인하고, 일시적인 요청 실패는 동일한 페이로드와 동일한 `X-Batch-Id`로 재시도하십시오.

## 레코드 라이프사이클

각 레코드의 이력은 append-only 이벤트 로그이며, Trace는 이를 타임라인으로 렌더링합니다. 각 단계는 정확히 하나의 값에 매핑되며, 해당 값이 존재하는 시점에 단계가 타임라인에 나타납니다.

| # | 단계 | 값 |
| --- | --- | --- |
| 1 | Captured | `timestamps.captured_at` |
| 2 | Uploaded | `timestamps.uploaded_at` |
| 3 | Attested | `attestation.signed_at_utc` |
| 4 | Registered | `DataRegistered` 이벤트(`seq: 0`)의 최상위 `occurred_at` |
| 5 | Anchored on-chain | `tx_hash` (DATA Foundation이 브로드캐스트하기 전까지 빈 문자열) |
| 6 | Updated | 각 `MetadataUpdated` 이벤트(`seq` 1–100)의 최상위 `occurred_at` |
| 7 | Payment credited | `timestamps.payment_credited_at` — 현재 저장되며 곧 타임라인에 표시될 예정 |

1–3단계는 등록 페이로드의 메타데이터에서 옵니다. 4–7단계는 감사 이벤트입니다. 각 마일스톤을 별도의 메타데이터 업데이트로 전송하십시오 — 하나의 마일스톤당 하나의 타임라인 이벤트입니다.

`occurred_at`은 두 위치에 존재하며 모두 provider가 제공합니다: 각 배치 항목의 루트 필드가 필수이며 이벤트의 날짜/시각을 지정합니다. `timestamps.occurred_at`은 attested 페이로드 내부에서 동일한 시점을 담습니다 — 이 둘은 동일하게 유지하십시오. DATA Foundation이 추가하는 값은 `ingested_at`과 `tx_hash`뿐입니다.

## Trace Schema v1.0

표준화된 Trace Schema 필드를 직접 채우고, 원본 공개 페이로드 전체는 `provider_payload` 아래에 보존하십시오. 정규화된 필드는 프런트엔드와 감사 흐름이 사용하는 이식 가능한 계약이며, provider 고유 정보는 어떤 것도 손실되지 않습니다.

- `initial_metadata_json` 및 `metadata_json`에서 `schema_version: trace-v1.0`을 사용하십시오. 값 자체는 검증되지 않으며 — `schema_version`이 누락되었거나 파싱 불가능한 경우 `trace-v1.0`으로 기본 처리되고, 어떤 값이 전송되든 이벤트 해시 계산에 반영됩니다.
- DATA Foundation은 내부 이벤트 해시 계산 전에 메타데이터 JSON을 canonicalize하므로 객체 키 순서는 idempotency나 충돌 감지에 영향을 주지 않습니다.
- 쓰기 페이로드에 트랜잭션 해시를 보내지 마십시오. `tx_hash`는 DATA Foundation이 소유하며, 등록, 메타데이터 업데이트, 검색 결과 행에 대한 읽기 응답에 반환됩니다 — 브로드캐스트 후 DATA Foundation이 채우기 전까지는 빈 문자열입니다.

### Canonical content hash (필수)

초기 등록 및 메타데이터 업데이트에는 하나의 canonical content hash가 포함되어야 합니다. 허용되는 필드는 `asset.hash`, `content_hash`, `file.content_sha256`, `file.hashes.sha256`이며, 모두 `sha256:<64-lowercase-hex>` 형태로 정규화됩니다. 두 개 이상의 alias가 존재하는 경우 동일한 해시를 나타내야 합니다.

### 검색 가능 필드(Searchable fields)

현재 exact-match 검색이 가능한 필드입니다:

| 필드 | Alias |
| --- | --- |
| `provider` | — |
| `source_record_id` | `media_id_public` (메타데이터에 존재하는 경우) |
| `file.content_sha256` | `asset_hash`, `asset.hash`, `content_hash`, `content_sha256`, `file.hashes.sha256` |
| `file.mime_type` | `mime_type`, `mimetype`, `file.mimetype` |
| `file.media_category` | `media_category` |
| `contributor.anon_id` | — |
| `collection_id` | `asset.collection_id` |
| `customer_id` | `asset.customer_id` |
| `task_id` | `asset.task_id` |
| `contributor.kyc_status` | — |
| `contributor.kyc_country` | — |
| `contributor.geo_region` | — |
| `tos_hash` | `contributor.consent.tos_hash` |
| `privacy_policy_hash` | `contributor.consent.privacy_policy_hash` |

검색 가능한 해시는 canonical content SHA-256뿐입니다 — perceptual 해시(`phash64`, `dhash64`, `ahash64`, `keyframe_phashes`) 및 `md5`는 저장은 되지만 인덱싱되지 않습니다. `app.platform_name`, `app.legal_entity`, `file.behavior.*`, `file_specific.base.motion.*`, `timestamps.payment_credited_at`도 동일합니다: 유용할 때 보내십시오 — 저장된 필드는 이전 데이터를 다시 보내지 않고도 추후 인덱싱이 가능합니다. 분포는 `/stats`를 사용하고, `provider`는 선택적 쿼리 범위로 사용하십시오.

### 필드 가이드

- `source_record_id` — provider가 소유하는 안정적인 공개 미디어 ID(예: `kmf_...`). 서비스는 주변 공백을 제거하고, 대소문자를 유지하며, 제어 문자는 거부하고, 최대 512바이트까지 허용합니다.
- `contributor.anon_id` — provider가 소유하는 공개 익명화 기여자 ID.
- `contributor.kyc_status` — 권장 값: `verified`, `pending`, `failed`, `unverified`.
- `contributor.kyc_country` — 가능한 경우 KYC에서 얻은 ISO 3166-1 alpha-2 국가 코드. 국가 코드만 사용하며, 주소나 GPS 기반 국가는 포함하지 않습니다.
- `contributor.tax_status` — 권장 값: `submitted`, `not_submitted`, `not_applicable`, `unknown`. `tax_form_on_file` 같은 boolean은 `true`를 `submitted`로, `false`를 `not_submitted`로 매핑하십시오.
- `contributor.account_verification_status` — 권장 값: `verified`, `pending`, `failed`, `unverified`.
- `contributor.consent.tos_*` 및 `contributor.consent.privacy_policy_*` — 이 레코드에 대해 기여자가 동의한 정확한 정책 버전, 해시, URI. provider 수준의 *활성* 정책은 레코드 페이로드 내부가 아니라 `PUT /webhook/v1/data-audit/provider-policy`를 통해 별도로 설정합니다.
- `attestation` — 스테이징에서는 서명이 선택 사항입니다. 프로덕션 검증에는 `payload_hash`, `signature`, `key_id`, `key_url`, `signed_at_utc`를 함께 전송하십시오.
- `app.legal_entity` — 앱/플랫폼 이름과 함께 법적 상대방 정보.
- `file.behavior` — 비-PII 캡처/업로드 행동 신호.
- `file_specific.base.motion` — 미디어 타입 전반에 걸쳐 공유되는 모션 신호.
- `timestamps.payment_credited_at` — provider가 기여자에 대한 지급을 최종 확정하고 정산한 시점의 선택적 UTC 타임스탬프. 정산되지 않은 경우(또는 지급이 몰수된 경우) 생략하십시오. 등록 이후에 지급이 이루어진 경우 전체 상태(full-state) 메타데이터 업데이트로 전송하십시오. 저장 전용(stored-only) 필드입니다.

## 쓰기 API

### 활성 provider 정책 설정

provider가 새로운 이용 약관(Terms of Service) 또는 개인정보 처리방침(Privacy Policy)을 게시할 때 이 엔드포인트를 사용하십시오. Trace는 활성 버전, 해시, URI를 저장하여 프런트엔드가 정책에 링크할 수 있게 하고, stats가 레코드를 정책과 비교할 수 있게 합니다.

<Note>
정책 행은 감사 전용입니다 — 인덱싱되거나 집계되지 않습니다. 레코드 페이로드는 여전히 `contributor.consent.*`를 담고 있으며, `/stats`, scoped 그룹 요약, 그리고 policy-hash 검색이 사용하는 것은 이 레코드 수준의 참조입니다.
</Note>

```http
PUT /webhook/v1/data-audit/provider-policy
Content-Type: application/json
X-API-Key: <provider API key>
X-Provider: kled
```

```json
{
  "tos": {
    "version": "2026-06-01",
    "hash": "sha256:<64-hex-policy-hash>",
    "uri": "https://kled.ai/terms/2026-06-01",
    "effective_at": "2026-06-01T00:00:00Z"
  },
  "privacy_policy": {
    "version": "2026-06-01",
    "hash": "sha256:<64-hex-policy-hash>",
    "uri": "https://kled.ai/privacy/2026-06-01",
    "effective_at": "2026-06-01T00:00:00Z"
  }
}
```

`tos`와 `privacy_policy` 객체는 모두 필수이며, 각각 `version`, `hash`, `uri`를 포함해야 합니다. `effective_at`은 선택 사항입니다. 해시는 asset 해시와 동일한 형식(`sha256:<64-hex>`, bare hex, `0x<64-hex>`, `0x1220<64-hex>`)을 받아들이며, canonical하게 `sha256:<64-lowercase-hex>` 형태로 저장됩니다. 요청 본문은 `1 MiB`로 제한됩니다.

현재 및 과거 정책 문서를 읽는 방법:

```http
GET /api/v1/data-audit/providers/kled/policy
GET /api/v1/data-audit/providers/kled/policies/tos/sha256:<64-hex-policy-hash>
```

`initial_metadata_root`는 canonical Trace Schema v1.0 메타데이터 JSON에 대한 provider의 결정적(deterministic) 0이 아닌 해시여야 합니다. DATA Foundation은 이 값을 제출된 그대로 저장하며, `initial_metadata_json`에 대한 해시 검증은 아직 강제되지 않습니다.

성공 응답(신규 항목이 큐에 등록된 경우 `202`, 모든 항목이 중복인 경우 `200`, 항목 중 하나라도 충돌한 경우 `409`):

```json
{
  "request_id": "story-request-uuid",
  "provider": "kled",
  "batch_id": "kled-records-000001",
  "format": "json",
  "kind": "records",
  "records": 1,
  "accepted": 1,
  "duplicates": 0,
  "conflicts": 0,
  "messages": 1,
  "items": [
    {
      "source_record_id": "kmf_8a9c2e7d4b1f0e23",
      "data_id": "story-generated-uuid",
      "status": "accepted"
    }
  ]
}
```

반환된 `data_id`는 이후의 메타데이터 업데이트와 읽기에 사용되는 canonical ID입니다. 동일한 `X-Provider` + `source_record_id`를 다시 보내면 동일한 `data_id`가 생성됩니다.

항목별 상태: 정확히 동일한 페이로드로 이미 저장된 항목은 `duplicate`를 반환합니다. 동일한 `source_record_id`이지만 *다른* 초기 메타데이터를 가진 항목은 `conflict`를 반환합니다. 이 둘 모두 (재)큐잉되지 않으며, 배치 내의 다른 유효한 항목은 영향을 받지 않습니다. 첫 번째 요청이 여전히 큐에 있는 동안 겹치는 재시도가 들어오면 `accepted`를 반환할 수도 있습니다 — 다운스트림 적재는 여전히 idempotent합니다.

호출자가 이미 DATA Foundation이 할당한 UUID를 보유하고 있는 경우, 더 낮은 수준의 `POST /webhook/v1/data-audit/data-ids:batch` 엔드포인트가 존재합니다. 이 엔드포인트는 모든 레코드에 `data_id`가 필요하며, 권장되는 provider 경로는 아닙니다.

### 메타데이터 업데이트 제출

이후의 수정이나 변경 가능한 메타데이터 변경에 이 엔드포인트를 사용하십시오. `seq`는 `data_id`별로 `1`–`100` 범위여야 합니다(모든 환경에서 레코드당 업데이트 하드 캡 100회). 동일한 provider 측 리비전에 속하는 변경 사항은 하나의 업데이트와 하나의 `seq`를 공유할 수 있습니다.

<Warning>
`metadata_json`은 canonical content hash를 포함해야 하며 **최신 Trace 메타데이터의 전체 상태(full latest Trace metadata state)** 여야 합니다 — diff나 patch가 아닙니다. KYC만 변경되었더라도 변경되지 않은 file, app, consent, provider payload 필드까지 모두 포함하여 각 이벤트가 `metadata_root`에 대해 검증되고 병합 규칙 없이 최신 상태를 재구성할 수 있도록 하십시오.
</Warning>

```http
POST /webhook/v1/data-audit/metadata-updates:batch
Content-Type: application/json
X-API-Key: <provider API key>
X-Provider: kled
X-Batch-Id: kled-metadata-000001
X-Ingestion-Source: backlog
```

요청 본문은 JSON 배열입니다:

```json

    "data_id": "11111111-1111-4111-8111-111111111111",
    "seq": 1,
    "prev_metadata_root": "sha256:<previous-canonical-trace-schema-v1-json>",
    "metadata_root": "sha256:<new-canonical-trace-schema-v1-json>",
    "metadata_json": {
      "schema_version": "trace-v1.0",
      "asset": {
        "hash": "sha256:<64-hex>"
      },
      "contributor": {
        "anon_id": "kup_123",
        "kyc_status": "unverified",
        "consent": {
          "tos_version": "2026-06-01",
          "tos_hash": "sha256:<64-hex-policy-hash>",
          "tos_uri": "https://kled.ai/terms/2026-06-01",
          "privacy_policy_version": "2026-05-20",
          "privacy_policy_hash": "sha256:<64-hex-policy-hash>",
          "privacy_policy_uri": "https://kled.ai/privacy/2026-05-20"
        }
      },
      "app": {
        "platform_name": "kled.ai"
```

`metadata_root`는 canonical한 업데이트된 전체 Trace Schema v1.0 메타데이터 JSON에 대한 provider의 결정적 0이 아닌 해시여야 합니다. `prev_metadata_root` 또한 0이 아닌 루트여야 합니다. DATA Foundation은 이 값들을 제출된 그대로 저장하며, `metadata_json`에 대한 해시 검증은 아직 강제되지 않습니다.

<Accordion title="선택적 백로그 파일 엔드포인트 (NDJSON / CSV / TXT)">

일반적인 통합 경로는 `/records:batch`의 `application/json`입니다 — 이 라우트는 JSON만 허용합니다. 백로그 도구를 위해 다음과 같은 더 낮은 수준의 라우트 변형도 존재합니다. 데이터 ID 파일 라우트는 모든 레코드에 `data_id`가 필요합니다.

```text
POST /webhook/v1/data-audit/data-ids:batch-ndjson
POST /webhook/v1/data-audit/metadata-updates:batch-ndjson
POST /webhook/v1/data-audit/data-ids:batch-csv
POST /webhook/v1/data-audit/metadata-updates:batch-csv
POST /webhook/v1/data-audit/data-ids:batch-txt
POST /webhook/v1/data-audit/metadata-updates:batch-txt
```

- **NDJSON**은 `Content-Type: application/x-ndjson`과 `Content-Encoding: gzip`을 요구합니다. 압축 해제된 각 줄은 JSON 엔드포인트와 동일한 필드를 가진 하나의 JSON 레코드입니다.
- **CSV**는 `Content-Type: text/csv`를 요구합니다.
  - 데이터 ID 컬럼: `data_id,source_record_id,initial_metadata_root,initial_metadata_json,occurred_at`
  - 메타데이터 업데이트 컬럼: `data_id,seq,prev_metadata_root,metadata_root,metadata_json,occurred_at`
  - `initial_metadata_json`과 `metadata_json`은 따옴표로 감싼 CSV 필드 안에 유효한 JSON이어야 하며 하나의 canonical content hash를 포함해야 합니다.
- **TXT**는 `Content-Type: text/plain`을 요구하며, 라인 구분 JSON, JSON 배열, 또는 동일한 CSV 컬럼을 사용하는 헤더 구분 쉼표/탭 텍스트를 받아들입니다.

</Accordion>

## 읽기 API

읽기 엔드포인트는 공개 감사 뷰입니다. `provider`는 선택 사항이며 범위를 좁히는 필터로 작동합니다.

읽기 모델:

- `GET /data-ids/{data_id}`는 등록 프로필과 최신 원시(raw) 메타데이터 이벤트를 반환합니다 — 저장된 최상위 시퀀스의 정확한 페이로드이며, 반드시 diff는 아닙니다.
- `GET /data-ids/{data_id}/metadatas`는 `seq: 0`의 등록과 이후의 메타데이터 업데이트를 포함하는 전체 append-only 메타데이터 이력을 반환합니다.
- 검색, 자산 영수증 조회, scoped 그룹 요약은 DATA Foundation이 해당 이벤트에서 도출한 정규화된 최신 상태 프로젝션을 사용합니다. 이 프로젝션은 MIME 타입, 미디어 카테고리, KYC 상태, TOS/privacy 버전, 라이프사이클 상태, `tx_hash`와 같은 필드를 제공합니다.


각 메타데이터 행은 `tx_hash`를 포함하며, 초기값은 빈 문자열입니다:

### 인덱싱된 필드로 검색

```http
GET /api/v1/data-audit/search?field=source_record_id&value=kmf_8a9c2e7d4b1f0e23
```

검색은 [검색 가능 필드](#검색-가능-필드searchable-fields)에서 exact-match로 수행됩니다. `source_record_id` 검색은 exact이며 대소문자를 구분합니다. 각 매치에는 `tx_hash`(초기값은 빈 문자열)가 포함되며, 응답에는 페이지네이션을 위한 `next_cursor`가 포함됩니다. `limit`은 기본 `100`이며 `1000`으로 상한이 설정되어 있습니다 — 그보다 큰 값은 거부되지 않고 조용히 클램프됩니다.

일반적인 흐름: 정확한 필드 값으로 레코드를 찾을 때는 `/search`를 사용하고, 감사 검증에 사용되는 canonical 이벤트 페이로드를 위해서는 `/data-ids/{data_id}` 또는 `/data-ids/{data_id}/metadatas`를 사용하십시오. 분포 카운트는 `/stats`를 사용하고, UI에 최신 레코드가 필요한 경우 `/recent` 또는 `/feed`를 사용하십시오.

더 많은 예시:

```text

GET /api/v1/data-audit/search?field=file.content_sha256&value=<64-hex-or-sha256-prefixed-hex>
GET /api/v1/data-audit/search?field=customer_id&value=<customer-id>
GET /api/v1/data-audit/search?field=task_id&value=<task-id>
GET /api/v1/data-audit/search?field=collection_id&value=<collection-id>
GET /api/v1/data-audit/search?field=contributor.consent.tos_hash&value=sha256:<64-hex-policy-hash>
GET /api/v1/data-audit/search?field=contributor.consent.privacy_policy_hash&value=sha256:<64-hex-policy-hash>
GET /api/v1/data-audit/search?field=collection_id&value=<collection-id>&provider=kled&limit=100&cursor=<next_cursor>
```

## Scoped groups

scoped 그룹은 Trace 프런트엔드나 파트너 리뷰어가 리뷰 세트에 대한 공개 스냅샷을 생성할 수 있게 해줍니다. provider 리뷰 워크플로우에서는 랩(lab)이 provider의 `source_record_id` 값을 제출해야 합니다. Trace는 결정적인 `data_id`를 계산하고 모든 레코드의 존재 여부를 검증한 뒤, 전체 세트가 유효한 경우에만 그룹을 생성합니다. (`hashes` / `hashes_text`를 통해 content 해시로부터 그룹을 생성할 수도 있으며, 두 입력 방식은 상호 배타적입니다.) 생성은 비동기적으로 이루어지므로, `GET /scoped-groups/{group_id}`를 폴링하여 `status`가 `complete`가 될 때까지 대기하십시오.

### 그룹 생성

```http
POST /api/v1/data-audit/scoped-groups
Content-Type: application/json
Idempotency-Key: kled-review-000001
```

source-record 그룹은 all-or-nothing 방식입니다:

| 조건 | 응답 |
| --- | --- |
| 중복된 `provider + source_record_id` 값 | `400` |
| 누락된 레코드 | `404` |
| 프로필/source 불일치 | `409` |
| 자산 프로젝션 없이 등록된 레코드 | `422` |

```http

Content-Type: application/json
```


### 그룹 읽기

```http
GET /api/v1/data-audit/scoped-groups/{group_id}
GET /api/v1/data-audit/scoped-groups/{group_id}/items?limit=100
GET /api/v1/data-audit/scoped-groups/{group_id}/items?limit=100&cursor=<next_cursor>
GET /api/v1/data-audit/scoped-groups/{group_id}/export.csv
```

`GET /scoped-groups/{group_id}`는 그룹 상태를 반환하며, 완료되면 `summary`에 집계 메트릭이 포함됩니다. `profile.status`는 `pending`, `processing`, `complete`, `failed` 중 하나입니다. `summary`는 그룹이 `complete` 상태일 때만 나타납니다.

`/items`는 제출된 각 `source_record_id`에 대해 확인된 `data_id`, `asset_hash`, receipt 요약과 함께 하나의 행을 반환합니다. cursor 기반 페이지네이션을 사용하며, 더 많은 행이 있는 경우 `next_cursor`를 반환합니다. `/items`와 `/export.csv` 모두 그룹이 `complete` 상태여야 하며, 그 전에는 `409`를 반환합니다. source-record 그룹의 경우 CSV export 컬럼은 `input_type,provider,source_record_id,data_id,asset_hash,status,mime_type,media_category,kyc_status,tos_version,privacy_policy_version,tx_hash`이며, hash-manifest 그룹은 대신 `hash,status,data_id,...`로 시작합니다.

## 제한 및 재시도 동작

| 제한 | 값 |
| --- | --- |
| 최대 webhook 배치 페이로드 (압축 해제된 크기) | `25 MiB` |
| 최대 provider-policy 요청 본문 | `1 MiB` |
| 최대 SQS 메시지 청크 | `240 KiB` |
| 최대 SQS 배치 페이로드 | `256 KiB` |
| 최대 직렬화된 레코드 크기 | `350 KiB` |
| data ID당 최대 메타데이터 업데이트 수 | `100` |
| 최대 인라인 scoped-group 본문 | `5 MiB` |
| 최대 인라인 scoped-group 해시 | `10,000` |
| 최대 인라인 scoped-group source record | `10,000` |
| 최대 source_record_id 길이 | `512 bytes` |

재시도 가이드:

- `502`, `503`, `504`, 네트워크 타임아웃, `429`는 지수 백오프와 지터를 사용해 재시도하십시오. (공개된 scoped-group create/upload 엔드포인트만 `429`를 반환하며 — IP당 분당 60 요청 — webhook 배치 엔드포인트는 결코 반환하지 않습니다.)
- 검증/인증 관련 `4xx`는 요청을 수정하기 전까지 재시도하지 마십시오.
- 재시도 시 `data_id`, 요청 본문, `X-Batch-Id`를 안정적으로 유지하십시오.
- `X-Ingestion-Source: backlog`는 백로그 작업에만 사용하십시오. 라이브 작업에서는 생략하십시오.
- 쓰기 경로는 동일한 `data_id`, 이벤트 키, 이벤트 해시에 대해 idempotent합니다.
- 동일한 `data_id`와 이벤트 키가 다른 메타데이터로 재시도되면 해당 레코드는 충돌로 처리되어 거부됩니다.

## 검증 규칙

| 규칙 | 동작 |
| --- | --- |
| 쓰기 엔드포인트에서 `X-Provider` 누락 | 요청이 거부됩니다. |
| 유효하지 않은 provider 이름 | 요청이 거부됩니다. |
| 설정된 allowlist에 없는 provider | 쓰기 요청이 거부됩니다. |
| API 키가 `X-Provider` 값에 대해 승인되지 않은 경우 | 쓰기 요청이 `403`으로 거부됩니다. |
| 쓰기 엔드포인트에서 `X-Batch-Id` 누락 | 요청이 거부됩니다. |
| `X-Ingestion-Source`가 `backlog` 이외의 값으로 존재하는 경우 | 요청이 거부됩니다. |
| `/records:batch`에서 `source_record_id` 누락 | 요청이 거부됩니다. |
| 하나의 `/records:batch` 요청 내에서 중복된 `source_record_id` | 요청이 거부됩니다. |
| 동일한 초기 등록 페이로드를 가진 기존 `/records:batch` 항목 | 항목이 `status: "duplicate"`를 반환합니다. |
| 다른 초기 등록 페이로드를 가진 기존 `/records:batch` 항목 | 항목이 `status: "conflict"`를 반환합니다. |
| 더 낮은 수준의 data ID 및 메타데이터 업데이트 라우트에서 UUID가 아닌 `data_id` | 요청이 거부됩니다. |
| `occurred_at` 누락 | 요청이 거부됩니다. |
| 유효하지 않은 `occurred_at` 타임스탬프 | 요청이 거부됩니다. |
| `1`–`100` 범위를 벗어나는 메타데이터 `seq` | 요청이 거부됩니다. |
| 누락되거나, 형식이 잘못되었거나, 0인 필수 metadata root 필드 | 요청이 거부됩니다. |

## 전달 시맨틱(Delivery semantics)

- 전달은 최소 1회(at least once)이므로 중복 제출이 발생할 수 있습니다.
- 동일한 이벤트의 중복 제출은 idempotent하게 처리됩니다.
- 동일한 `data_id`, 동일한 메타데이터 시퀀스, 서로 다른 이벤트 내용은 충돌로 처리됩니다.
- 메타데이터 업데이트가 초기 data ID 등록 이전에 도착할 수 있습니다.
- 감사 데이터는 영속적이며 만료되지 않습니다.
- 이벤트 해시는 canonicalize된 메타데이터 JSON과 event/hash/schema 버전 필드로부터 계산됩니다.
